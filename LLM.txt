## 2026-03-31 - Phase 2: Remove Redundant CSS Fallback Values

### What was done
- Removed 211+ redundant `var(--moka-TOKEN, FALLBACK)` inline fallbacks from 39 `.razor.css` files
- Three pattern types cleaned: `#hex` fallbacks, `rgba()` fallbacks, and `var()` token-to-token fallbacks
- Preserved component-local custom properties (e.g., `--moka-swatch-columns`, `--moka-popover-offset-x`)
- All tokens are defined in `moka.css` `:root`, so removing inline fallbacks is safe

### Why this matters
- Single source of truth: changing a token value in `moka.css` or via `MokaTheme` now takes effect everywhere
- No more drift risk where inline fallbacks silently preserve stale values
- Cleaner CSS that's easier to read and maintain

## 2026-04-08 - Docs preview-host overhaul + 0.1.6 FrameworkReference fix

### What was done
- **Bumped to 0.1.6** in `Directory.Build.targets`. The 0.1.5 release intended to fix
  NETSDK1082 for WASM consumers but only added the `Microsoft.AspNetCore.Components.Web`
  PackageReference substitution - the implicit `Microsoft.AspNetCore.App` `FrameworkReference`
  was still being added by the SDK and propagated into the published nuspec.
- Added a new MSBuild `<Target Name="StripAspNetCoreAppFrameworkRef"
  BeforeTargets="_CheckForUnsupportedNETCoreVersion;ProcessFrameworkReferences;ResolveFrameworkReferences">`
  in `Directory.Build.targets` that runs for `IsPackable=true` projects and removes
  `Microsoft.AspNetCore.App` from the FrameworkReference items collection BEFORE the SDK's
  unsupported-version check fires.
- Verified by extracting `Moka.Red.0.1.6.nupkg`'s nuspec - `<frameworkReferences>` group is
  no longer present (vs. 0.1.3 which had it for both net9.0 and net10.0 targets).
- Deleted `nuget.config` - the file only had `<clear /> + nuget.org` which is the global
  default, so the file was redundant. Removed to avoid confusing future contributors.

### docs/ overhaul
- `docs/mokadocs.yaml` - replaced the verbose `previewHost: …`, `references: […]`,
  `stylesheets: […]` plugin block with a single `library: Moka.Red@0.1.6` line. The
  `mokadocs-blazor-preview` plugin (v3.x in `mokadocs` repo) now auto-discovers a
  `./preview-host/` Blazor WebAssembly project, scaffolds it from a generic library-
  agnostic template if missing, and runs `dotnet publish` on it transparently. The yaml
  no longer points across the repo boundary at the sibling `Moka.BlazorRepl` repo.
- The auto-scaffolded `docs/preview-host/` project (csproj + Program.cs + wwwroot/index.html
  + empty Directory.* shadow files) is owned by the user after first scaffold; mokadocs
  never overwrites it. Edit `Program.cs` to register library-specific services and
  `wwwroot/index.html` to add CSS/font links between the customization markers.

### Files modified
- `Directory.Build.targets` - bumped Version to 0.1.6, added `StripAspNetCoreAppFrameworkRef` Target
- `CHANGELOG.md` - added [0.1.6] entry
- `docs/mokadocs.yaml` - replaced previewHost/references/stylesheets with `library:` field
- `nuget.config` - deleted

### Build result
- `dotnet pack Moka.Red.slnx -c Release -o nupkgs` - all 12 packages packed at 0.1.6, 0 errors
- `Moka.Red.0.1.6.nupkg` nuspec verified to have NO `<frameworkReferences>` group

### The bugs that actually mattered

**MokaBarcode was lying about four of its five formats.** `MokaBarcodeFormat` advertises
Code128/Code39/EAN13/EAN8/UPC but every value routed to `GenerateCode128`. Code 39, EAN-13,
EAN-8 and UPC-A are now real encoders with check-digit computation and validation, L/G/R parity
tables, proper guard patterns and per-format quiet zones (the old renderer drew flush to the
canvas edge, which makes any symbol unscannable). 14 new tests assert the spec module counts
(95/67/95), guard offsets, and that UPC-A equals EAN-13 with a leading zero.

**MokaMarquee never scrolled at all.** `animation-duration: calc(100vw / var(--speed) * 1s)` is
invalid CSS - calc cannot divide a length by a length - so the declaration was dropped entirely.
Duration is now computed in C# and `IsVertical` (previously computed and unused) selects the
loop distance.

**EditForm validation was invisible library-wide.** `MokaInputBase.ComponentCssClass` had zero
consumers, so the framework's `modified`/`valid`/`invalid` classes never reached the DOM, and
`HasError` was purely `!string.IsNullOrEmpty(ErrorText)` in every component. Added
`ValidationMessages`/`HasValidationError`/`ValidationErrorText` to the base and wired 11
components through it. 8 new tests render a real `EditForm` + `DataAnnotationsValidator` and
assert the message appears.

**MokaTable had ~13 parameters with no UI behind them.** Filter row, inline editing, keyboard
navigation, row reordering and column resizing were all declared and unreachable; `RowReorderable`
even rendered a header cell with no matching body cell, so every data row was one short. All
wired. Also fixed: `<Virtualize>` in `<tbody>` without `SpacerElement="tr"`, an unchecked
`ICollection<T>` cast, boxing that made expand rows never open for struct items, and
`SelectedItems` being aliased rather than copied.

**Only one dialog could ever be shown.** A second `ConfirmAsync`/`ShowAsync` overwrote the pending
`TaskCompletionSource` and the first `await` never completed. Requests now queue, `Close(false)`
resolves to `false` rather than `null`, and `Dispose` resolves everything pending. 10 new tests.

**CSS isolation was silently breaking selectors.** Converting inline `<svg>` to `<MokaIcon>`
moves the element into MokaIcon's scope, so `.moka-chip__close svg` stops matching - the rewriter
appends the scope to the last compound selector. Six components needed `::deep`, and that also
repaired pre-existing dead rules on usages that were already MokaIcon.

**Duplicate bare selectors.** `MokaCallout` had five `.moka-callout__icon` rules (one per type);
only the last applied, so the per-type icon colours never rendered. `MokaStat` had three size
variants with the same problem, where a hardcoded `32px` won.

  also disables hot-reload page refresh. WasmApp's profile has launchBrowser true so dotnet watch

- mokadocs: detects the installed global tool, compares against the latest on NuGet, offers
  install/update, and can run from the sibling Moka.Docs source instead.

### Bugs found by testing it (all fixed before shipping)
- `find` and `ping` resolved to Git for Windows' Unix tools when they come first on PATH. Unix find
  treats "," as a directory; Unix `ping -n` means numeric output and pings forever, which would have
  hung the browser waiter. Both pinned to System32, along with timeout.exe.
- `pause` hitting end of input on a pipe leaves the next `choice` blocked forever. Replaced with
  `timeout /t -1`, which waits for any key at a console but returns immediately when input is
  redirected.
- The waiter counted loop iterations, but probing a closed localhost port costs ~2s on Windows, so
  "240" meant ~13 minutes. Now time-capped through curl's retry options.
- `mokadocs validate` is a stub ("not yet implemented"), so the menu no longer offers it.

## 2026-10-12 - Tooltips that stuck after a click (0.1.18)

Mokaterm reported its icon tooltips (top bar, settings, terminal) as sometimes buggy. Three causes, all in `MokaTooltip`:
- The shown state matched `:focus-within`, so a button that kept focus after a click kept its tooltip once the mouse
  had gone, and got it back whenever a menu or dialog handed focus back to it. It is `:has(:focus-visible)` now, the
  rule the focus ring follows.
- `Delay` was a `transition-delay` on the popup, so hiding waited as long as showing. The component sets
  `--moka-tooltip-delay` instead, which only the shown state reads; the base rule has `transition-delay: 0s`.
- The popup was absolute inside its trigger, so any ancestor that clipped its overflow cut it off. Under
  `@supports (anchor-name: ...)` it is `position: fixed` against an anchor its trigger names (`anchor-name` on the
  trigger, `position-anchor` on the popup, one GUID name per instance), placed with `position-area` and moved with
  `position-try-fallbacks`. A centred popup that would cross a side edge is shifted along by the browser. Browsers
  without anchor positioning keep the old placement and 0.1.17's edge placements.

Checked in the DevApp and in the Mokaterm DevHost on a local pack: a clicked Settings button keeps focus and shows no
tooltip, Tab shows it, a Top tooltip at the top of the window lands below, a Right one at the right edge lands on the
left, a 24 px `overflow: hidden` box no longer clips it, and `container-type` does not capture fixed positioning in
Chromium. A draggable dialog keeps its centring transform, which does capture it, so inside one the popup is held to
the dialog's box.

## 2026-10-18 - Menu bar, hotkey registry, table grouping, validation summary (0.1.21)

BC asked what was worth adding next. Probed the registry rather than guessing: there is no menubar (MokaMenu
is sidebar nav, MokaDropdown is one button's menu), nothing owns a key binding, the table has no grouping, and
there is no validation summary. BC picked all four, plus two bugs.

**The two bugs first.**

- `MokaKeyValue` drew every copy button with the default "Copy", so a list of them gave a screen reader a row
  of identical buttons. `CopyLabel` defaults to "Copy " and the key's `Label`, with `CopiedLabel` and
  `CopyTooltipPosition` passed through. BC left the case question open: the default keeps the label's case,
  because lower-casing mangles the acronyms these labels are full of (IP, API, SHA-256) and because a name
  matching the visible text is what WCAG's Label in Name wants. `MokaCopyButton` grew `DefaultTooltipText` and
  `DefaultCopiedText` consts so the fallback is not a second copy of the literals.
- `MokaStatusBarItem.Class` could not reach the tooltip wrapper, which is the status bar's actual flex item.
  BC offered `display: contents` as an option "only if anchor positioning, hover and keyboard focus still
  work; test that before choosing it". Measured it in the DevApp: with `display: contents` on the trigger the
  popup lost its anchor and moved about 90px away from the item, because the trigger carries the tooltip's
  `anchor-name` and an element with no principal box cannot be an anchor. So `TooltipClass`/`TooltipStyle`,
  documented as the place layout goes while `Class` keeps styling the item.

**The four features.**

- **MokaMenuBar** (+ Menu, Item, Divider) in Navigation. Keyboard in C# rather than a JS module: the items are
  the component's own, so a roving `tabindex` computed in C# is deterministic and testable, and `preventKeys`
  from `moka-keys.js` cancels the arrows and Home/End one key at a time. Keydown is handled on the bar, not
  per menu, because a key pressed inside an open menu still has to move between the menus beside it.
- **The hotkey registry** in Core, which is the only package everything else can reach. `MokaHotkey`,
  `IMokaHotkeyService`, `MokaHotkeyService`, `MokaHotkeyHost` and `AddMokaHotkeys()` (called from
  `AddMokaRed()`). Matching is in `moka-hotkeys.js`, not .NET: a keydown that round-tripped before it could be
  rejected would send every keystroke over a Blazor Server circuit. The command palette's own parser and
  matcher moved into that module and the palette imports them, so there is one matcher rather than two copies.
  `MokaCheatsheet` with no `Groups` now lists the registry, which is the point of the whole thing: the
  shortcut list cannot drift from the bindings because it is the bindings.
- **Table grouping**: `GroupBy` plus `GroupHeaderTemplate`, `GroupsCollapsible`, `InitiallyCollapsedGroups`
  and `OnGroupToggled`. Grouped in order of first appearance, each group keeping its rows in the order it had
  them, so grouping gathers and the sort still orders. Grouping wins over `Virtualize`.
- **MokaValidationSummary** in Forms. The first draft grew field links and a reflection walk over the model's
  properties to find which field each message belonged to; cut it, because a control's id is generated per
  field wrapper and a message carries no way back to it. It lists `GetValidationMessages()`, which is what
  Blazor's own summary does, themed and announced.
- **MokaInfiniteScroll** got its first tests (known issue 4), including the one for the guard that used to
  wedge the component when `OnLoadMore` threw.

**Three things the tests and the browser caught that review would not have.**

- `[Inject]` does a *required* resolve even for a nullable property, so the cheatsheet's optional
  `IMokaHotkeyService` broke every existing cheatsheet test the moment it was added. Resolved through

- `StateHasChanged()` only queues the render, so the menu's items did not exist when the bar asked it to

- Both cascades were written with `IsFixed="true"`, which is exactly what rule 14 forbids: the menus read the

## 2026-11-01 - the 0.2.0 session

The version plan BC approved: the dialog earns placement modes, backdrop effects, an exit animation

fatal. The format information bits were written most-significant first along the module path, which
mirrors all fifteen bits on both copies - no reader can learn the level or the mask from that, at
any version. And the EC block counts were wrong from V5 up (V5-Q/H two blocks instead of four,

component test that parses the rendered SVG's rects, proves they paint exactly the generator's
grid, and decodes that. Capacity is 2953 bytes at Low now (V40, up from 271 at V10), with the
alignment positions and codeword counts computed from the standard's formulas instead of tables -
hand-transcribing the block table a second time drifted at V19+, which the capacity anchors caught
immediately. Generate the tables from the reference source; do not type them.

## 2026-11-04 - A closed tab logs nothing

MokaGate's router UI, on 0.2.0, logged a `CircuitHost[111]` error and a `RemoteRenderer[100]` warning
for every page with a dialog that someone closed or reloaded: a `TaskCanceledException` out of
`MokaDialog.ImportJsModuleAsync`, awaited by `DisposeAsyncCore`, and another out of the module's own
`DisposeAsync`. When a Blazor Server circuit ends, Blazor disposes its components, and a JS call that
was already on its way is cancelled rather than refused, so it arrives as `TaskCanceledException`, not
the `JSDisconnectedException` 72 catch blocks in src expected.

- **`MokaJsInterop`** (new, public, `Core/Base`): `IsCircuitGone(ex)` = `JSDisconnectedException`,
  `OperationCanceledException` (so `TaskCanceledException`) or `ObjectDisposedException`, never
  `JSException`; `SafeInvokeVoidAsync` (returns false when the call did not land) and
  `SafeDisposeAsync` as extensions on `IJSObjectReference?` (null does nothing). Every
  `catch (JSDisconnectedException)` in src is now `catch (Exception ex) when
  (MokaJsInterop.IsCircuitGone(ex))` or one of the extensions; the separate ODE/OCE catches beside them
  were folded in. `grep JSDisconnectedException src` finds only the helper.
- **`MokaComponentBase.DisposeAsync` and `MokaInputBase.DisposeAsync`** swallow a circuit-gone
  exception from `DisposeAsyncCore` (a consumer's too), and dispose the cached module in a `finally`,
  so it goes even when the cleanup throws. Anything else still propagates. Note what that means for
  a derived cleanup: the steps after the failing call are skipped, which is why the components use
  the extensions step by step instead of leaning on the net.
- **Teardown starts no import.** MokaDialog and MokaBottomSheet still await an import started in
  `OnInitialized` (needed to release the trap and the scroll lock, and to dispose the module), but
  `ImportJsModuleAsync` now returns null for a cancelled import instead of throwing. Every other
  disposal call is guarded by a flag that means the module already exists.
- Leaks found on the way: `MokaBrowserTabStorageProvider.DisposeAsync` (a scoped service, so it is
  disposed with the circuit's scope) had no catch at all; MokaReveal's and MokaSortable's first-render
  imports had none either.
- Tests: `tests/Shared/EndingCircuit.cs` (linked into Core.Tests and Feedback.Tests) has `EndingModule`,
  an `IJSObjectReference` that answers until `End()` and then fails every call and its disposal with
  `TaskCanceledException` (bUnit's module references never fail to dispose), and `ControlledImport`,
  an import handler the test completes or cancels. `MokaDialogTeardownTests` (4) and
  `MokaComponentBaseTeardownTests` (3). Narrowing `IsCircuitGone` back to `JSDisconnectedException`
  fails five of the seven; the other two are the controls (a live circuit; a real bug in a cleanup
  still surfaces). 2679 tests, all green; the solution builds with 0 warnings.
- Docs: `api/base-classes.md` says what the safe helpers absorb now and grows "JS calls in
  teardown". CHANGELOG has an `[Unreleased]` entry for 0.2.1. Nothing committed, packed, tagged or
  pushed.

## 2026-11-07 - MokaAppShell under Trusted Types, and the drawer's focus

## 2026-11-10 - buttons keep their labels in a flex row

MokaArk's setup card cut its footer buttons to "Open a vaul" and "Change serve". `.moka-btn` had `overflow: hidden`, which
makes a flex item a scroll container, and a scroll container's automatic minimum width is 0, so the footer squeezed the
button below its label. `overflow: clip` clips the same way without being a scroll container, so the button keeps a
minimum width of its content, as a native button does, and a button given a width still ends its label with an ellipsis.
Chosen over `flex-shrink: 0`, which would also stop a full-width button from shrinking. With buttons that no longer shrink,
a row too narrow for them runs out of its box, so `MokaDialog`'s actions and both `MokaWizard` button rows wrap; they hold
only buttons. `MokaCard`'s footer doesn't: plain wrapping split MokaArk's footer, leaving one button alone on a second row,
where one row lets the text wrap beside the buttons. The WASM smoke test now checks a squeezed card footer in a browser,
and it fails on the old rule.
